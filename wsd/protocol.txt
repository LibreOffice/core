All communication consists of messages that are one line of
human-readable UTF-8 text (with no terminating newline), optionally
followed by a single newline and arbitrary (potentially even binary)
data.

The WebSocket distinction between 'text' and 'binary' frames has no
meaning for us for messages that don't contain additional binary data;
such messages can be either 'binary' or 'text' from the WebSocket
point of view even if we require them (the single line) to be
UTF-8. In other words, an implementation is free to send such a
single-line message as a WebSocket 'binary' frame, and the receiving
implementation must treat that equally as if it was a 'text' frame.

The WebSocket protocol says that 'text' frames are to be "interpreted"
as UTF-8, so it is probably best to indeed use 'binary' frames for
messages that contain optional non-UTF-8 data.

The protocol is not a request-response one. Messages may be sent in
either direction at any time, either in response to some message, or
spontaneously. For 'tile' messages, the client may send a bunch of
tile requests without waiting for return messages. The server may send
tiles proactively (guessing what the client might need). Etc.

The original intent was that the parameters of the messages can be in
any order, as they are in a name=value form anyway and the name
indicates which parameter is which. Sadly, this was not explicitly
mentioned in this document, or tested by unit tests. So now we have
code here and there that assumes that parameters are in a specific
order anyway, thus losing the benefits of the named parameters. Oh
well.

When the document is password protected, it already implies that the
document didn't load, and that with the proper password we should try
again. Similarly for when the password given is wrong. However, if
loading fails and it isn't a password-related failure,
faileddocloading error is returned and in this case the client handles
it as a final error (that requires reloading to retry).

client -> server
================

A convention: Messages that have the first token (keyword) in
UPPERCASE are related to debugging and tracing of the client and
server software and not related to the user's actions.

DEBUG <rest of message>

    The rest of the message (without the DEBUG keyword), possibly
    multiple lines, is logged by the server as LOG_DBG.

ERROR <rest of message>

    The rest of the message (without the ERROR keyword), possibly
    multiple lines, is logged by the server as LOG_ERR.

TRACEEVENT name=<name> ph=<letter> ts=<timestamp> <more parameters>... [ args=<JSON.stringify-string> ]

    Timestamps and durations are in microseconds, from
    performance.now(), multiplied by 1000, and rouded to an integer.

    name is a string of non-space characters.

    ts is the timestamp when the trace event was generated.

    ph is one of the following, and the rest of the parameters depend
    on what it is.

    'i': An "Instant" event.

    'S', 'F': The start and finish of an "Async" event. In addition to
    the name, the messages have an "id" parameter, a unique number
    that must be the same for the 'S' and 'F' messages.

    'X': A "complete" event. The "dur" parameter is the duration
    between the beginning of the thing being timed and the time when
    the 'X' message was emitted, also in microseconds.

    args is an optional parameter, and its value is a JSON string
    where the keys and values are strings with no spaces in them.

tileprocessed wids=<wid1,wid2,...>

    Previously sent tile (server -> client) arrived and processed by the client.
    We send a list of wire-ids back for tiles that have been received.

downloadas name=<fileName> id=<id> format=<document format> options=<SkipImages, etc>

    Exports the current document to the desired format and returns a download URL
    The id identifies the request on the client. id can take following values:
    * 'print': When request for download is basically for print purposes
    * 'slideshow': When request for download is for showing slideshow
    * 'export': Just a simple download

remotedocsubscribe source=<encoded persistent link>
remotedocunsubscribe source=<encoded persistent link>

    Subscribes the sending view to, or unsubscribes it from, live events
    about the remote document bound to the given persistent link. A view
    names a remote document by its persistent link alone, and the address
    the server reaches it at stays with the server. The subscription
    belongs to that one view and is opened with that view's own access
    token for the remote document; the token comes from a POST to
    /cool/links, or from that view's storage answering over
    <WOPISrc>/linkaccess. A view
    without a token for the source is refused, and so is a persistent link
    no remote link is bound to. A remotelinkremove of the persistent link
    drops the document for every view, and the subscriptions to it go down
    with it. A view holds at most one subscription per source. The command
    is handled inside wsd and never given to this document's kit. Requires
    the remote_links feature to be enabled.

remotelinkresolve source=<encoded persistent link>

    Asks this view's storage for the document behind one of the persistent
    links the open document's pages record, over a POST to
    <WOPISrc>/linkaccess. A view asks for the sources it finds on the
    document once, when it joins; afterwards, and for the sources later
    editing names, this command is the only thing that asks, so a user who
    sees a source reported as missing can have it looked for again.
    Requires the remote_links feature and SupportsLinkAccess.

remotelinkremove source=<encoded persistent link>

    Drops the remote link bound to the given persistent link from the list
    of this document, for every view. The subscriptions to it go down with
    it, and the fresh list goes out to all views. The link is named by its
    persistent link, the value the document's pages store, and not by the
    address the storage resolved it to. Answered with an error of kind
    'notfound' when no remote link is bound to it. Requires the remote_links
    feature to be enabled.

remotedoccommand source=<encoded persistent link> <inner client command>

    Routes a read-only client command to the remote document the current
    document is subscribed to, bound to the given persistent link. The inner command is an
    ordinary client command line, for example "getslidesections" or
    "tilecombine ...". The command is handled inside wsd and sent to the
    remote over the headless session; it is never given to this document's
    kit. Only non-modifying commands are accepted. The remote's replies come
    back as remotedoccommandresult: messages. Requires a live subscription to
    the source.

callextension <callId> <extensionId> <kind> <name>
<arguments>

    Call a function of the installed code of the extension <extensionId> in the kit's JS UNO, and
    reply via 'executescriptresult:' tagged with the same <callId>.  <arguments> occupies everything
    after the first newline and is a JSON array of the arguments, where an empty <arguments> stands
    for no arguments.  <kind> is one of

    * 'remote': the function <name> that the files that the "remote" field of the extension's
      manifest.json lists add to the object 'remote'
    * 'gas': the function <name> of the Apps Script add-on, run through the GAS runner of the kit
      with the add-on's code files and libraries, with the arguments [<proxyId>, [<arg>, ...]]
    * 'listen' or 'unlisten': add or remove the built-in listener for the document event <name>
      ('selectionChanged' or 'modified'), which calls the JS-UNO proxy whose ID is the only argument

    The server looks the extension up among the extension presets of the document's configuration
    first, then among the built-in extensions.  When it cannot make a call of the message, it
    replies with an 'executescriptresult:' whose "err" gives the reason.  <callId> is an opaque
    string that the client picks for matching the resulting 'executescriptresult:'.

proxyreturn <callId> <json-value>

    Deliver the JSON-encoded return value of a JS-UNO listener proxy invocation back to the kit-side
    proxy stub (which is spinning in Application::Yield waiting for it, cf. ProxyInvocation::invoke
    in engine/jsuno/source/jsuno.cxx).  <callId> is the id that was sent out in the corresponding
    'proxycall:' (whose payload contains a non-null callId iff the invoked listener method has a
    non-void return type).  Only meaningful while a 'proxycall:' is still outstanding; spurious or
    late 'proxyreturn' messages are silently ignored.

insertfile name=<name> type=<type>

    Inserts the file with the name <name> into the document, we currently
    support:

        type = 'graphic': The file has been previously uploaded using insertfile POST

        type = 'graphicurl': The file is supposed to be downloaded by the core
	                     itself; it does so from the URL provided in 'name'

        type = 'comparedocuments': The file has been previously uploaded using insertfile POST

        type = 'videobackground': The file has been previously uploaded using insertfile POST.
                                  It becomes the looping, muted video background of the master
                                  slide of the current slide, replacing any it had.

        type = 'comparedocumentsurl': The file is downloaded from the URL provided in 'name'.
                                      coolwsd downloads a URL on the WOPI host of the document
                                      itself, with the WOPI proof headers, and the core gets the
                                      downloaded file. coolwsd follows a redirect within that
                                      host the same way. The core downloads a URL on any other
                                      host itself, including another WOPI host.

    In the mobile apps the message carries the file itself as data=<base64>
    after the type, since the app cannot upload. There it also takes:

        type = 'filepicker': Answers the 'filepicker:' request whose id is given
                             as id=<n> after the data, the way 'filepickerresult'
                             does on the server. <name> is URL-encoded and has the
                             shape "<number>-<file name>", and the engine gets the
                             file under its own file name. A name of another shape,
                             or a file that cannot be written, gets an error and
                             ends the request with no file.

selectbackground name=<name>

    Inserts a graphic file with the name <name> into the document as background.

filepickerresult id=<n> [name=<name>]

    Answers the 'filepicker:' request with id <n>. <name> is the name of a
    file previously uploaded using the insertfile POST, URL-encoded here and
    plain in the upload form. It has the shape "<number>-<file name>", and
    the engine gets the file as a file URL inside the jail, in a directory of
    its own under its own file name. Without a name, the user cancelled and
    the request ends with no file. A name of another shape, or a file that
    cannot be moved, gets an error and also ends the request with no file.

linkpickerresult id=<n> [path=<path>]

    Answers the 'linkpicker:' request with id <n>: <path>, percent-encoded, is
    the path of the picked file relative to the document, as the integration
    gave it in Action_PickLinkedFile. Without a path, the user cancelled. The server
    asks the storage for the file the way it does for linkedfile list, stages
    the copy and tells the kit
        linkpickerresult id=<n> path=<path> file=<staged name>
    or linkpickerresult id=<n> when the storage gives no file. The server takes
    an answer to the last 'linkpicker:' request of the session only, and the
    kit takes the answer of the server alone; it never gets the client's.

slideimport insert file=<staged name> [source=<source name>] [slides=<i0,i1,...>]
                   [at=<S>] [keepdesign=<0|1>] [link=<0|1>] [time=<source time>]
                   [sourcepositions=<p0,p1,...>]
                   [as=<slides|section|presentation>] [id=<source section id>]
                   [name=<source unit name>]

    Inserts pages of a presentation staged in the jail into the open document.
    Only Impress documents are served. The staged name is the file a remote
    link wrote when it was asked to exportslides, which the server put in
    the staging area of this document's jail; the insert takes it, so the file
    leaves the staging area whether the pages are inserted or not. Slide
    indices are 0-based standard-page indices, and no list at all inserts every
    page of the file.

    The pages are inserted before slide <S>; a missing or out-of-range <S>
    appends them at the end. keepdesign=1 copies the design of the file along;
    keepdesign=0 makes the inserted pages adopt the design of this document.

    <source> names the source document as the user knows it, percent-encoded
    like the staged name: a document name holding no path. link=1 keeps the
    inserted pages bound to it, so that they can be refreshed from it later;
    link=0, or no link at all, inserts plain copies. <source time> is the time
    the source was last modified now, percent-encoded, recorded on the linked
    pages so a later comparison tells whether they are up to date.

    <sourcepositions> names the position each inserted page's slide holds in
    the source, counted from one, in the order the staged file holds the pages:
    one position per page or none at all. A page inserted with a position is
    linked to that position rather than to one slide, so an update reads
    whichever slide stands there; a page inserted without one is linked to the
    identifier of the slide it came from.

    as= says what the pages go in as. as=slides, the default, inserts them as
    slides. as=section inserts them as a section of their own that holds the
    section of the source they make up: <source section id> names that section
    by the identifier the source reports for it in slidesections:, and <source
    unit name> its name, both percent-encoded and both given. The section
    is named like the source section. With link=1 the section is linked to the
    source section, so that a later update can add and remove slides as the
    source section gains and loses them; without it the section is a plain
    section of this document. The pages go in at <S>. A section ends where the
    next one starts, so the pages that follow them get a section of their own:
    a section that started at <S> starts after the new pages, and the rest of
    the section the pages went into keeps its name in a section of its own, or
    takes the default name when it was in no section. as=presentation inserts
    every page of the staged file at <S>, in the sections of that file, with
    the pages outside any section first in a section named <source unit name>,
    the name of the source document, which a presentation insert gives and
    which is not empty. With link=1 the whole presentation is linked to the
    source, and so is each section the file identifies, the section of the
    pages outside any section, and each page; without it they are plain
    sections and slides of this document. A section insert takes no
    sourcepositions, a presentation insert takes no slides=, no sourcepositions
    and no id=, and a slides insert takes no id= and no name=; an insert of any
    other shape is answered kind=syntax. The slides, the sections and their
    links are one undo step. A source section id that is no GUID, or a name
    longer than 128 characters, inserts nothing and is answered kind=syntax.
    The reply is
        slideimport: {"status":"inserted","count":<K>}

    Errors are reported as
        error: cmd=slideimport kind=<syntax|cantload|failure|nosource>
    where cantload means no file is staged under that name, failure covers an
    insert the document refused, including one a view that cannot edit asked
    for, and nosource means an insert that asks for links without naming a
    source document.

exportslides [slides=<p0,p1,...>|guids=<g0,g1,...>]

    Writes the given pages of this document out as a presentation of their own,
    named by the part identifiers a presentationinfo: reports, or by the
    identifier each page keeps in ODF, which is what a document holding pages
    read from this one records for them. No list at all writes every page out.
    The reply is the presentation itself, as a binary frame
        exportslides: {"status":"written"}\n<the file>
    so a document is reached the same way whichever node serves it.

    One export carries at most 100 MB, as the file travels as one frame and is
    held in memory whole. The pages are written before their size is known, so
    a document whose chosen pages come to more than that is answered
        exportslides: {"status":"failed","kind":"toolarge"}
    and no file travels with it.

    A client of this document sends it through remotedoccommand, to a document
    this one is related to, and wsd takes the reply: it writes the file into the
    staging area of this document's jail and answers the client with the name it
    was staged under alone,
        exportslides: {"status":"staged","name":"<staged name>"}
    or {"status":"failed"} when it could not be staged. A path of another jail
    is nothing a client is given. The staged name is what a slideimport insert
    or a slidelink update then names.

    Writing pages out takes the content of the document into a file of its own,
    so a host that allows no export, or that has what leaves the document
    watermarked, is answered
        error: cmd=exportslides kind=failed
    before any page is written.

linkedfile list

    Reads the files that sections of a text document link to, the chapters of
    a master document for example. The reply is
        linkedfiles: {"links":[{"id":"<path>","url":"<url>","section":"<name>",
                                "filter":"<filter>","readable":<true|false>},...]}
    one entry per linked section. <path> is the path of the file relative to
    the document, as plain text and not percent-encoded, with / between its
    folders, as chapter1.odt or ../shared/chapter2.odt,
    url is where the document resolves it, left out for a client of the server,
    as it names a file in the jail, section the section that shows it,
    filter the filter that reads it, and readable whether the kit can read it,
    from where it is or from a copy the server gave it. A document that links
    to nothing, and a document that is not a text document, gives an empty
    list.

    When CheckFileInfo says SupportsRelativeLinkAccess, the server asks the
    storage for the files the kit cannot read, once the user of a view that
    may change the document allowed its links to be updated (allowlinkupdate):
    it POSTs
        {"Kind":"relative","RelativePaths":["<path>",...]}
    to <WOPISrc>/linkaccess, with at most 64 paths of at most 1024 bytes each.
    Only relative paths are asked for: not one from the root, a URL or a
    drive. The storage answers
        {"Links":[{"RelativePath":"<path>","Status":<status>,
                   "WOPISrc":"<WOPISrc>","AccessToken":"<token>"},...]}
    resolving each path against the folder of the document. The path comes
    out of the content of the document, so the storage gives a file only when
    the user may read it, and decides whether a path that leads out of the
    folder of the document by .. is answered. An entry whose
    Status is not 200, absent counting as 200, and a path without an entry,
    are files the storage does not give. For the others the server downloads
    <WOPISrc>/contents with that access token, only from the WOPI host of the
    document, into the staging area of the jail, and gives the copy to the kit
    with linkedfile source. The kit reads the file from the copy for the rest
    of the session, and the document keeps linking to the path it had. The
    question, the copies and the answers of the kit to them are the server's
    own and are not sent to the client. The content of a copy, fetched with
    the access of one user, becomes content of the document: every view of
    the document shows it, and a master document that saves the content of
    its links as well keeps it.

    When the user asks to read the linked files anew, with Update in the
    Navigator of a master document for example, the kit tells the server
        linkedfilesrefresh: <the list as in linkedfiles:>
    with the files the user asked for, every file or those of the sections
    the user chose. The server asks the storage for every file of the list
    again, the readable ones too, and gives the kit fresh copies the same
    way: a copy is what the storage had when it was made. In the apps the
    message goes to the client, and the client of the Android and the iOS
    app posts
        LINKEDFILESREFRESH <the list>
    to the app. The Android app copies the files again from the folder trees
    the user allowed and sends linkedfile source for the fresh copies; the iOS
    app reads the files through file coordination, which brings a file of a
    cloud provider up to date, and sends allowlinkupdate. The desktop apps
    read the files where they are and need neither.

    With SupportsRelativeLinkAccess the server also sends linkedfile
    enablepick to the kit, once a view that may change a text document loaded
    it, so that the Navigator of a master document offers Insert > File: the
    user picks the file in the storage, see 'linkpicker:'.

linkedfile source id=<path> file=<staged name>

    Sent by the server alone, never by a client: the kit reads the linked file
    with the path <path> from the file staged as <staged name>. Both are
    percent-encoded. The reply is
        linkedfile: {"status":"registered","id":"<path>","count":<sections>}
    or error: cmd=linkedfile kind=<syntax|failed|notlinked>.

    In the apps, where the client is the app's own, the app sends it, and
    file= may be a file URL of a copy the app made or of the file where the
    app may read it. After a load, the client of an app sends linkedfile list
    for a text document, and when files are not readable it offers the user
    to allow access, posting
        GRANTLINKEDFILES {"links":[<the unreadable entries of linkedfiles:>]}
    to the app, which asks the user for the folder, makes the files readable
    with linkedfile source or in place, and sends allowlinkupdate.

originaldocumenturl url=<file URL>

    Sent by an app that works on a copy of the file the user opened, when it
    saves the copy as another file: the URL, percent-encoded, of that file.
    The relative links of the document are written for it from then on. Only
    an app sends it.

slidelink list
slidelink break unit=<slide|section|presentation> id=<id> [deep=<0|1>]
slidelink update source=<source name> file=<staged name> [time=<source time>]
                 [unit=<slide|section|presentation> id=<id>] [name=<unit name>]

    Reads the links the document holds to the slides, the sections and the
    whole decks of other documents, refreshes them from a source, and takes a
    link off. Only Impress and Draw documents hold such links. A link holds a
    copy of one unit of a source document, a slide, a section or the whole
    presentation, in a run of slides of this document. A source is the
    persistent link of the source document, the
    value a link records: the reference the storage resolves to that document,
    which is no address the server reads itself. The server matches it against
    the remote links of the document, and for one no remote link stands for it
    asks the storage, when CheckFileInfo says SupportsLinkAccess; a refresh
    then reads the remote link it stands for. A source name is any text without
    a control character, at most 1024 bytes long. The source name, the WOPISrc
    and the staged name are all percent-encoded.

    A client sends all three. An update names a file the server staged in the
    jail, which is what an exportslides of a remote link comes to, so the kit
    reads only a file of its own jail and never a location. An update may add
    a time, the time the source was last modified now, which the refreshed
    links record so a later comparison tells whether they are up to date.

    A break and an update name a unit of this document by unit= and id=
    together: the unit is slide, section or presentation, and <id> the
    identifier the link list reports for it, a GUID, percent-encoded. The two
    may come in any
    order among the optional tokens, and each token of a command comes once. A
    unit of another kind, an identifier that is no GUID, or one of the two
    tokens without the other is answered kind=syntax.

    list: the reply is
        slidelinks: {"links":[{"unit":"<slide|section|presentation>","id":"<id>",
                               "parent":"<id>","source":"<source document>",
                               "sourceId":"<id>","name":"<name>",
                               "lastModifiedTime":"<time>",
                               "slides":["<part>",...]},...]}
    one flat array in document order: a presentation, then the sections it
    spans, each followed by the slides it spans. The unit says what the link
    holds a copy of: one slide of the source, one section of it, or the whole
    presentation. <id> is the part of the linked page for a slide, the
    identifier of the section for a section, as the slidesections list names
    it, and an identifier of the link's own for a presentation. parent is the
    innermost link that spans the unit: the section that spans a slide, else
    the presentation that spans it, or empty. source is the source document.
    sourceId is the slide or the section in the source: the identifier of the
    source slide, the name a slide holds by its position when the link follows
    a position, or the identifier of the source section. It is empty for a
    presentation, and for the section of a presentation that holds the slides
    of the source outside any section, which names no section of the source.
    name is the name the slide or the section had in the source when it was
    last read, empty for a slide that has no name of its own, or the name of
    the source document for a presentation and for that section.
    lastModifiedTime is the time the source was last modified when the unit
    was last read, empty when none was recorded; comparing it with the
    source's current time tells whether the link is out of date. slides lists
    the parts the link spans, in slide order. A page linked to a file by its
    path is no link of this list, since a refresh has no way to reach it. A
    document that links to nothing reports an empty array.

    A link holds while its unit spans the slides it was linked with, in that
    order: the one page for a slide, the same slides in the same order for a
    section, and the same sections in the same order for a presentation. A
    slide inserted into a section, removed from it or moved within it ends the
    link of the section, and the section is then left out; undoing the change
    puts it back. A section added to a presentation, taken out of it or moved
    within it ends the link of the presentation the same way. A slide that an
    edit took its own link off stays among the slides of its section, and a
    section that lost its link stays among the sections of its presentation.
    The kit sends the list on its own, to
    every view of the document, whenever the links listed there change: when a
    link is made or taken off, when an edit of a linked page or of the slides
    of a section ends a link, and when an undo or a redo brings it back. A
    client therefore learns of a link that went or came back without asking
    for the list again, and so does every other view of the document,
    whichever view made the change.

    break: takes the link off the unit it names, which keeps the slides it
    holds and becomes a unit of this document alone, so a later refresh of
    that source leaves it as it is. With deep=1 every link beneath comes off
    as well: each slide of a section loses its link to its source slide, as a
    break of each slide would do, and so does each section and each slide of a
    presentation. With deep=0, or with no deep=, the links beneath stay. This
    is one undo step, and undoing it gives every link back. The reply is
        slidelink: {"status":"broken","unit":"<slide|section|presentation>","id":"<id>"}
    A unit that is linked to nothing is answered kind=notlinked, a view that
    cannot edit kind=failed, and a deep= that is neither 0 nor 1 kind=syntax.
    The fresh link list arrives on its own, as above.

    update: refreshes the links to <source name> from <staged name>, a file
    previously uploaded using the insertfile POST that holds the slides of that
    source. This is the message wsd sends the kit once it has the content of a
    source as a local file. The kit reads only the staged file, never a
    location, and removes the file once the refresh is done. With no unit,
    every link of the source that is under no other link is refreshed: each
    linked slide outside a linked section or presentation, each linked section
    outside a linked presentation with the slides it spans, and each linked
    presentation with the sections and the slides it spans. With unit= and id=
    that one link alone is refreshed, and
    the other links to the source keep their slides and the time they record;
    a unit that is not linked to <source name> is answered kind=notlinked. The
    whole refresh is one undo step.

    A slide is read from the file by the identifier of its source slide, or by
    its position when the link follows one. A section is read by the identifier
    of its source section, which the file lists among the sections of its
    pages, and holds a fresh copy of each slide of that section and no other
    slide, in that order, so slides added to the source section come in, slides
    taken out of it go, and a slide edited in this document is replaced as
    well; a client asks the user before it sends this. A presentation is read
    whole, every page and every section of the file: a section the file still
    lists is read again in place and keeps its identifier here, a section new
    to the file comes in, one the file no longer lists goes, and the pages
    outside any section stay in the section named after the source document.
    The slides keep the design of the source, as a refreshed page does. <unit
    name> is the name the unit has in the source now, percent-encoded, and
    goes with a unit; for a presentation it is the name of the source
    document. Without it a section takes the name the file lists for its
    source section, since the file carries the sections of its pages under the
    names they have in the source, and a presentation keeps the name it
    recorded. A section follows that name while its own name is still the name
    the source section had at the last read, and keeps a name given to it in
    this document. A unit the file holds nothing for, or whose slides
    could not be read, keeps the slides it holds, and those slides are
    reported. Each refreshed page is the page read for it, so it holds a new
    part; the reply is therefore the fresh link list followed by
        slidelink: {"status":"updated","source":"<source document>",
                    "unit":"<slide|section|presentation>","id":"<id>",
                    "count":<K>,"notUpdated":["<part>",...]}
    where unit and id are those of the command and are left out when it named
    none, <K> counts the slides refreshed, and notUpdated lists the parts of
    the slides the file held nothing for.

    Errors are reported as
        error: cmd=slidelink kind=<syntax|notlinked|failed>
               [source=<source name>] [unit=<slide|section|presentation> id=<id>]
    where notlinked means no link of the document is to that source, that the
    unit an update names is not linked to it, or that the unit a break names
    is linked to nothing, and failed means the staged file could not be read,
    or the view cannot edit. An answer of an update names the source it was
    sent for, and an answer of a break or of an update that carries both unit=
    and id= names them as the command spelled them, so that a reader of these
    messages tells the answers of one command of the family from those of
    another. A command too malformed to say what it was for names neither.

    Provides the password that allows editing a document that has a
    separate password for modifying. Such a document loads in
    read-only mode, and every view stays read-only until it has sent
    the correct password with this message. Only the view that sent
    the password becomes editable: the other views stay read-only
    until each of them sends the password itself.

    <password> is URL-encoded, so it can contain spaces.

        editwithpassword: success

    and the view can switch to edit mode. On failure an error is
    returned:

           otherwise there are no guarantees of any sensible
           compatibility. This is bumped when API changes.

Part identifiers of a presentation or drawing document are the pages'
GUIDs in braced form, {1BE1A269-4A03-4202-ACFE-0204C5E9BE1F}, not indexes
into the page list. The identifiers carry no order: to reach a
neighbouring page, find the page's position in the status message's page
list and take the identifier listed next to it. The status message lists
each page's identifier as part, in document order. A page keeps its
identifier when other pages are moved, inserted or deleted, and across
save and reload when the file format stores it (extended ODF and OOXML
do). Because the tile cache keys carry the part identifier, the cached
tiles of a page stay valid when the page order changes. The identifiers
of the pages a mode addresses come from that mode's page list: the
standard pages, the master pages, the notes pages, the notes master
pages or the handout master page. Every message that
names a part uses these identifiers for such documents - the tile,
tilecombine, setclientpart, selectclientpart and getslide requests, and
the tile:, delta:, invalidatetiles:, setpart:, curpart: and status:
(selectedpart) responses. The load message's part option takes either
form, a page identifier or a positional index. Text and spreadsheet
documents use plain part indexes throughout, written in decimal form.

setobjecttransform to=<mappings> as=<what> [sequence=<sequence>]

    <mappings> holds one item per object, separated by semicolons. An item is the unique id of a
    drawing object, the one the render geometry of a page names it by, then the six numbers of
    the mapping it is to be drawn by - a, b, c, d, e and f - all separated by commas. The
    mapping takes the object's own square, whose corners are 0 and 0 and 1 and 1, onto the
    page, in twips: the first corner goes to e and f, and the other four numbers say which way
    and how far its own two axes run. A mapping whose two axes are turned over against each
    other turns the object over. <what> is "move", "scale", "turn" or "shear", and names the
    step it can be undone with.

    Gives every one of those objects the mapping named: it keeps what it is and only its place,
    its size, its turn and its shear become what the mapping says. The whole of it is one step to
    undo. A client that works a drag out for itself hands over what it drew this way, rather than
    asking for a handle of the selection to be moved.

setobjectcontrolpoint id=<id> at=<at> x=<x> y=<y> withtheshape=<withtheshape> [sequence=<sequence>]

    <id> is the unique id of a drawing object, the one the render geometry of a page names it by,
    and <at> counts the points a custom shape is shaped by, from zero, in the order the shape
    offers them. <x> and <y> are where that point is to go on the page, in twips.
    <withtheshape> is 1 to carry the shape along where the point is one that moves it, which is
    what the tail of a callout does when it is dragged without a modifier, and 0 otherwise.

    The shape reads such a point as the value it shapes itself from and holds it to whatever that
    value may be, so the place named here is a wish and what the shape makes of it is the answer.
    One step to undo. Naming an object that is not a custom shape does nothing.

    <id> is the unique id of a drawing object, the one the render geometry of a page names it by,
    and the four after it name one of that object's handles as the render geometry reports it:
    <kind> is the kind of handle, <polygon> and <point> say which point of which polygon it
    belongs to, and <at> is the number the object itself gives the handle, for the handles that
    are told apart by nothing else. <at> is -1 where the three before it already name the handle.

    The object reads such a move its own way: the corner radius of a rectangle, the angle a piece

    A point a custom shape is shaped by is not moved this way: it has setobjectcontrolpoint,
    which says in the command whether the shape is carried along, where this one would leave

setobjectpoints id=<id> changes=<changes> [as=<step>] [sequence=<sequence>]

    <id> is the unique id of a drawing object, the one the render geometry of a page names it by.
    <changes> names the points and weights of that object's path which moved, were added or were
    removed. It is a list separated by semicolons, and the items apply in the order they come. A
    move is six numbers separated by commas:

        <polygon>,<point>,<part>,<x>,<y>,<continuity>

    <polygon> counts the polygons of the path from zero and <point> counts the points of that
    polygon from zero, in the order the render geometry lists them. <part> is 0 for the point
    itself, 1 for the weight that bends the curve coming into it and 2 for the weight of the
    curve going out of it. <x> and <y> are where that point or weight went, in twips.
    <continuity> says how the curve is to run through that point: 0 for a corner, 1 for a point
    it runs smoothly through, 2 for one it runs symmetrically through.

    An addition is a plus sign and four numbers separated by commas:

        +<polygon>,<point>,<x>,<y>

    It adds a point with no weights at <x> and <y>, in twips, that takes the index <point> in
    the polygon. <point> can be one past the last point of the polygon. The points after it count
    one more in the items that follow. A weight of the new point is set by a move after the
    addition.

    A removal is a minus sign and three numbers separated by commas:

        -<polygon>,<point>,<part>

    With <part> 0 it removes that point with its weights, and the points after it count one less
    in the items that follow. With <part> 1 or 2 it removes the weight of that point, 1 for the
    one coming in and 2 for the one going out. The edge on that side is then bent only by the
    weight at its other end, and it is a straight line when that end has no weight either.

    A polygon that points were removed from keeps two points at least, and it goes when no point
    of it is left. The path keeps one polygon at least, so deleting the last points of a path is
    deleting its object.

    <step> names the step in the undo list: "move", the default, "add", "delete", "continuity",
    "curve", "line" or "simplify". An addition belongs to the step "add", a removal of a point to
    the steps "delete" and "simplify", and a removal of a weight to any step but "move" and
    "delete". The step "delete" has nothing but removals of points, and the step "simplify" has
    nothing but removals. A message with any other step, or with an item that does not belong to
    its step, changes nothing.

    Changes those points and leaves every other point of the path untouched, in one step that can
    be undone. Moving one weight of a point that is run through smoothly or symmetrically carries
    the other weight of that point along, and the continuity that is named is then set exactly,
    so a point whose numbers had drifted a little off comes out lying on the line. A move or a
    removal of a weight that is not written as above, or that names a point the path does not
    have, is left out. An addition the path has no place for, or a point to remove that the path
    does not have, changes nothing at all, because the items after it would name other points.
    So does a message that leaves a polygon with one point or the path with no polygon.

splitobjectpath id=<id> polygon=<polygon> point=<point> [newid=<newid>]

    <id> is a drawing object, as for setobjectpoints. <polygon> and <point> are the index of a
    polygon of its path and of a point in that polygon, as for setobjectpoints. Splits the open
    path into two objects that meet at the point, as one undo step, so the point cannot be one
    of its ends. Only a path of one polygon with three points or more can be split. The second
    object holds the part after the point and takes the id <newid>, which is one of the ids
    reserved for this view. Without <newid> it takes an id of its own. A <newid> that another
    object on the page has changes nothing.

setobjectpathclosed id=<id> closed=<closed> [at=<at>]

    <id> is a drawing object, as for setobjectpoints. <closed> is 'true' or 'false'. Closes the
    path by adding an edge from its last point to its first, or opens it by removing that edge,

    points. With <at>, which is "<polygon>,<point>" as for setobjectpoints, a closed path of one
    polygon with three points or more is opened at that point instead, and the point becomes
    both of its ends, so no edge is lost. <at> goes only with 'false'.

textcursor object=<objectId> paragraph=<paragraph> index=<index> [anchorparagraph=<paragraph> anchorindex=<index>] [sequence=<sequence>]

    paragraph. With an anchor, the text from the anchor to the caret is
    selected, otherwise no text is selected.

      as the invalidatecursor payload reports it in its object field. When
      another object or none is being edited, the caret stays where it is.

      primitives of its page name it, and the caret goes to that frame

remotelinks: <json>

    The remote links the server tracks for this document, from POST
    /cool/links and the storage's answers over <WOPISrc>/linkaccess
    (WOPISrc, BaseFileName, LastModifiedTime and PersistentLink per
    entry), and from the sources the document's own slide
    links name. A remotelinkremove takes one off the list, for every view,
    and the fresh list goes out to all of them. Built for the receiving
    view: the source list is the same for every view, but the state is
    that view's own, and the name and last-modified time of a source are
    given only to a view that holds a token for it. Sent to a view when it
    joins and again when the shared list or that view's own access or
    subscription state changes. Access tokens and the addresses of the
    remote documents are never included: a view knows a remote link by its
    persistent link alone. The JSON carries a documents array of entries:

        { "name": "<the BaseFileName the integrator gave the document, or the
                    file name at the end of its WOPISrc, for a view that holds
                    a token for it; the persistent link for any other view>",
          "lastModifiedTime": "<time for a view that holds a token, else empty>",
          "state": "noaccess|available|subscribed|connected|disconnected|failed|missing",
          "error": "<why the subscription is failed or missing, or empty>",
          "persistentLink": "<the reference the document's pages store for the source>",
          "access": "pending|resolved|notfound|denied|failed, or empty" }

    'noaccess' means the view holds no token for the source. 'available'
    means the view holds a token but has no live subscription. The other
    values follow the connection events of the view's subscription, which
    the remotedocevent message in the parent -> child section lists. A
    subscription the server refused stays listed as 'failed', so the view
    asks for the source again only on purpose.

    'error' is the kind the server or the remote document gave a 'failed'
    or 'missing' subscription, and it is empty for every other state and
    when no kind was given. Among the kinds are 'cycledetected' for a
    subscription that would link the documents in a circle, 'chaindepth'
    for one that would chain more documents than the server allows,
    'limitreached' for one over the number of remote documents or links
    the server allows, and 'disconnected' for a live link that was lost
    for good.
    'missing' means the source cannot be read: either it could not be read
    from storage, or it is a document the open one names as the source of
    its slides that no remote link stands for. Such an entry carries its
    name alone, so it says what the slides were made from while nothing can
    reach it; its persistentLink is that name.

    'access' is what asking this view's storage for the persistent link came
    to, and it is empty for a source this view never asked for, which is
    every source on a storage that does not answer link access requests.
    'pending' means a question is in flight, 'notfound' that the storage
    knows no document for the link, 'denied' that this view's user may not
    reach it, and 'failed' any other answer or none. A source that is
    'resolved' is the remote link the storage named. See remotelinkresolve
    for asking again.

remotedoccommandresult: source=<encoded persistent link>\n<inner server frame>

    A reply from a remote document to a remotedoccommand. The header line
    names the remote by the persistent link its remote link is bound to;
    everything after the first newline is
    the frame the remote node sent, verbatim, text or binary (for example
    slidesections:, status:, tile:, sendthumbnail:). The frame is delivered
    only to the view that issued commands to that remote, so several remote
    documents can be driven in parallel and told apart by the persistent
    link.

error: cmd=<command> kind=<kind> [code=<error_code>] [params=1,2,3,...,N]
<freeErrorText>

    <command> is the command part of the corresponding client->server
    message that caused the error.

    <command> can also take following values:
    'internal': for errors generated without directly corresponding to a client
    message.
    'storage': for errors pertaining to storage (filesysytem, wopi etc.)

    <kind> is some single-word classification

    <code> (when provided) further specifies the error as forwarded from

close: <reason>

    Ask a client to close the websocket connection with <reason>.
    Exactly similar fields are also available in WebSocket protocol's
    CLOSE frame, but some browser implementation (google-chrome) doesn't seem to
    handle that well. This is a temporary application-level close websocket
    to circumvent the same.

    <reason> can have following values:
    * ownertermination - If the session close is due to 'Document owner'
    terminating the session.
    (Document owner is the one who has the file ownership and hence have the
    ability to kill all other sessions if EnableOwnerTermination flag in WOPI
    CheckFileInfo is 'true' (assumed to be 'false' by default).

    * shuttingdown - Sent when the server is going down in a graceful fashion.
    The server doesn't disconnect from clients yet, but starts
    saving document and tearing down internals.

    * recycling - The last message sent from the server when it is gracefully
    shutting down to let clients know they can try connecting
    after a short interval.

    * documentconflict - All sessions of this document are going down
    because file was changed in storage and we want to load the new document
    from the storage.

    * versionrestore payload - Version restore message is also sent as part of
      the close frame. See `versionrestore:` message for details.

    <name> is the resulting name (without path) that was created on the wopi
    host. It can differ from what was requested in case the file already existed.

status: type=<typeName> parts=<numberOfParts> current=<currentPartNumber> width=<width> height=<height> viewid=<viewId> hiddenparts=<part1,part2,...> selectedparts=<part1,part2,...> [partNames]

    <typeName> is 'text, 'spreadsheet', 'presentation', 'drawing' or 'other. Others are numbers.
    if the document has multiple parts and those have names, part names follow separated by '\n'

statusupdate: type=<typeName> parts=<numberOfParts> current=<currentPartNumber> width=<width> height=<height> viewid=<viewId> hiddenparts=<part1,part2,...> selectedparts=<part1,part2,...> [partNames]

    Same as status: but issued whenever the document parts have updated significantly.
    status: implies document loading (deprecated, use loaded: instead). statusupdate: is just an update.

    For a presentation or drawing document the selectedpart field of the
    JSON payload carries the current page's part identifier, the page's
    GUID, and each entry of the parts array carries its page's
    identifier as part, in document order.

    For a text document the JSON payload has a pageids array: the id of
    each page as a string, in the order of pagerectangles. A page keeps its
    id while it exists, and .uno:VectorPrimitives names a page by it. When
    the ids change, a vectorpartids: message says so. A document that has
    no page ids leaves the field out.

    The first status: after a reconnect that gave the client its old view
    back has "reattached": true. The view still has its cursor, selection,
    part and dialogs in the kit.

    A master document, a text document that links its chapters, has
    "masterdocument": true, whatever the name of its file is.

vectorpartids: {"pageids": [<id>, ...], "pagerectangles": [[<x>, <y>, <width>, <height>], ...]}

    The list of the pages of a text document changed: a page was added or
    removed, or a page took the place of another. Sent to every session of
    a document that served a page as vector primitives.

    pageids is the id of each page as a string and pagerectangles is the
    rectangle of each page in twips. Both are in page order, both have one
    entry for each page, and both have the meaning of the fields of the
    same name in status:. The two arrays describe the same moment, so the
    page with the id at an index lies at the rectangle at that index.

    The message carries no document size. When the size changed too, a
    status: follows as for any other size change. A session that was
    inactive when the list changed gets a status: instead when it is
    active again.

styles: {"styleFamily": ["styles in family"], etc. }

statechanged: <key>=<value>

    Notifies client of state changed events of <key>.
    Eg: 'statechanged: .uno:Undo=enabled'

    The security-label lifecycle event is a special statechanged whose value is a
    JSON object rather than a scalar, and which coolwsd broadcasts to every session
    of the document (the classification banner it drives is client-side chrome, not
    document content). It is emitted when a label is applied, changed or removed:

        statechanged: {"commandName":".uno:SecurityLabel","state":{
            "action":"applied"|"changed"|"removed",
            "classification":<new classification, empty on removed>,
            "marking":<new visual marking, empty on removed>,
            "oldClassification":<prior classification, empty on applied>,
            "oldMarking":<prior visual marking, empty on applied>}}

    The client updates its banner from "marking" and, for an action-bearing change,
    posts a Security_Label_Changed message to the host integration (see the SDK
    postMessage API). The separate on-load 'commandvalues command=.uno:SecurityLabel'
    seeds the banner without an action and is not broadcast.

    The text edit lock event is a statechanged whose value is a JSON object. It
    tells this view that it and another view both want to edit the text of one
    shape:

        statechanged: {"commandName":".uno:TextEditLocked","state":{
            "viewId":<the other view>,"part":...,"mode":...,"reason":...,
            "event":<a number that differs in each of these messages>}}

    The reason is one of these:
    "refused": this view tried to edit the text, but the other view edits it.
    "takenover": the other view took the text edit from this view.
    "requested": the other view asks this view to leave the text it edits.
    "rejected": the other view goes on with the text after this view asked.
    "returned": the other view gave the text edit back to this view.
    .uno:RequestTextEdit, .uno:TakeOverTextEdit and .uno:ReturnTextEdit
    take the "objectId" of the viewlock message as an ObjectId string, and
    do nothing when that view no longer edits that shape. Only the view that
    a shape was taken over from gets it back, and only while its user can
    edit. .uno:RejectTextEditRequest answers only a view that asked for the
    text that this view edits now.
    The engine does not check how long a view has not typed. The client
    decides when to offer a take over. A view that is inactive gets the
    last "takenover" or "returned" of each other view once it is active
    again.

viewposition: [editmode=1] [zoompercent=<percent>] [x=<twips> y=<twips> width=<twips> height=<twips>]

    Sent once, after the status that follows the load, when the document kept
    the position of the view that left it before this one arrived. editmode is
    present when that view was in editing mode. x and y are the top left corner
    of the area it had in view, in document twips, followed by its size.

    Only a CODA client sees this. A document keeps the position of a view that
    goes away while the app keeps the document open but detaches its view, which
    is what CODA does when it drops excess tab contents, and on reattach sends this.

textselectioncontent:
<JSON>

    Current selection's content, only for text-only selections of a reasonably limited size.
    For complex selection and large texts, selectioncontent message is returned.
    The keys of the JSON are MIME types (text/html, text/plain;charset=utf-8),
    the values are the content of the selection in that format.
    For debug/test purposes, in case a single MIME type is requested, that's
    returned as-is, not inside a JSON.

complexselection:

    Complex selections with embedded objects and large text selections need special export handling.
    This response signifies that the payload is large and/or complex and needs to be retrieved via the clipboard API.

aichatresult:<json>

    Response from the AI chat assistant. The JSON payload contains:
    - success: Boolean indicating if the request succeeded
    - content: The AI response text (on success, for text responses)
    - imageData: Base64-encoded PNG image data (on success, for image responses)
    - error: Error message (on failure)
    - requestId: The request identifier from the original 'aichat' message

executescriptresult: <json>

    Reply to a 'callextension' message.  The JSON payload has the shape

        { "id": <callId> [, "ok": <jsonValue>] [, "err": <error>] [, "legacyUnoApi": true] }

    Exactly one of "ok" or "err" is set, except when the script's result value was something
    JSON.stringify drops (undefined, a function, a symbol), in which case neither key is present,
    which the client-side helper surfaces as a Promise resolving to JavaScript undefined.

    "err" is either a plain string (for engine-level failures without structured context, e.g.
    QuickJS not enabled in this build) or a structured object

        { "message": <string>, "name": <string>, "stack": [<frame>, ...] }

    where each <frame> is

        { "source": <string>, "line": <string>, "column": <string>, "functionName": <string> }

    naming the (1-based) JS coordinates QuickJS attributed to the throw site (i.e. relative to the
    <startLine>/<source> that were passed on the corresponding 'executescript').

    "legacyUnoApi" is present and true iff the script touched the legacy com.sun.star UNO API, used
    by the client to flash a one-time deprecation snackbar.

proxycall: <json>

    Notification that a UNO listener proxy installed via an earlier 'callextension' has been invoked
    from UNO.  The JSON payload has the shape

        { "proxyId": <string>, "callId": <string>, "method": <string>, "args": [...] }

    "callId" is present iff the proxy stub is waiting for a synchronous return value via
    'proxyreturn' (i.e. the listener method has a non-void return type; for void return types the
    call is fire-and-forget).

consolemsg <level>
<message>

    Notification that a script running under a 'callextension' called one of the WHATWG Console API
    methods jsuno registers on the global `console` object: log, info, warn, error, debug, trace or
    assert.  <level> is that method name; <message> occupies everything after the first newline and
    is the stringified-and-space-joined args the script passed.  For "trace" and "assert" the JS
    stack at the call site is appended to <message> (as extra "    at ..." lines); "warn" and
    "error" carry the JS stack the same way, so that browser-side rendering of the message names the
    kit-side call chain and not the client-side postMessage plumbing that delivered it.  "assert"
    only fires when the assertion failed; the other methods fire on every call.  The client-side
    helper routes each event to console[<level>] in the browser.

tile: part=<partNumber> width=<width> height=<height> tileposx=<xpos> tileposy=<ypos> tilewidth=<tileWidth> tileheight=<tileHeight> [timestamp=<time>] [wid=<wireId>]
<binaryPngImage>

    The parameters from the corresponding 'tile' command.

    WireId is a monotonically incrementing, unique reference to a
    state of the document on the server, and can be included by
    the client in the next 'tile' message requesting the same tile.

    the tile message has at least one keyframe, followed by any
    number of concatentated compressed deltas.

delta: part=<partNumber> width=<width> height=<height> tileposx=<xpos> tileposy=<ypos> tilewidth=<tileWidth> tileheight=<tileHeight> [timestamp=<time>] [wid=<wireId>]

    A delta command is like a tile: command but the payload is purely
    an incremental patch on top of a previous tile.

commandresult: <payload>

    This is used to acknowledge the commands from the client.
    <payload> is { command: <command name>, success: 'true' }

Each LOK_CALLBACK_FOO_BAR callback except
LOK_CALLBACK_INVALIDATE_TILES causes a corresponding message to the
client, consisting of the FOO_BAR part in lowercase, without
underscore, followed by a colon, space and the callback

invalidatecursor: <payload>

    The payload contains a rectangle describing the cursor position
    and the id of the view which triggered the invalidation. JSON payload.
    When the client numbers its inputs, the payload also carries
    inputSequence, the newest input applied before the cursor was placed.
    While a drawing object's text is edited, object is the unique id of
    the object that holds the caret, as the vector primitives name it.
    For a shape in a group, it is the group member being edited.
    In a text document, object is the id of the text frame that holds
    the caret, as the vector primitives of its page name it, paragraph is
    0 and index is the offset of the caret in the text of the frame's
    paragraph, which the text portions of the frame index their text by.
    A drawing object in a text document is named by the id of its entry
    in the vector primitives of its page: its unique id plus 4294967296,
    which lies above every frame id.
    While text is selected in an edit text, anchorParagraph and
    anchorIndex give the other end of the selection, in the same terms as
    the caret's paragraph and index.

    The communication between the parent process (the one keeping open the
    Websocket connections to the clients) and a child process (handling
    one document through COKit) uses the same protocol, with
    the following additions and changes:

unocommandresult: <payload>

Callback that an UNO command has finished.
See LOK_CALLBACK_UNO_COMMAND_RESULT for details.

invalidateviewcursor:

    Per-view cursor position invalidation. JSON payload.

    "objectId" is there while the rectangle is not "EMPTY". "existing" is

viewinfo: <payload>

    Message is sent everytime there is any change in view information.
    <payload> consists of an array of JSON objects. Structure of JSON
    objects is like : {"id": <viewid>, "username": <Full Name of the user>}

    Each object also carries "parked": "true" or "false" (literal strings).

    Signals that the user chose Edit for a file a master document links to,
    which the engine does not open itself. <payload> is a JSON object with the
    URL the document resolves the file to, its path relative to the document,
    and the name of the section that shows it, for example
    {"url":"file:///.../chapter1.odt","id":"chapter1.odt","section":"chapter1.odt"}.
    The server leaves out the URL, which names a file in the jail.
    The apps open the file in a window of their own. In a browser the client
    posts UI_OpenLinkedDocument to the integration, with RelativePath and
    SectionName in its Values, and the integration opens the file the path
    names relative to the master document.

    A document made of the current one, the master document Create Master
    Document makes in a desktop app, comes with its URL only, as
    {"url":"file:///.../book.odm"}, and the app opens it the same way.

    views of the document. Sent to every view, the one that turned it on

    view, for example {"viewId": "1"}.

comment:

a11yfocuschanged: <payload>

    Sent while screen reader support is on:
    - when the view starts with screen reader support on;
    - when the accessibility focus goes to another paragraph, or the
      paragraph that has it changes, and its text, headingLevel, area,
      links, formats, changes, images, comments or contentControls differ
      from what was last sent;
    - when editing the text of a selected shape or a spreadsheet cell
      starts, and when editing a cell ends;
    - when text is selected in a formula being edited, such as a cell
      reference picked with the mouse.
    When the caret goes to a paragraph in a Writer table, or out of all
    tables, a11yfocusedcellchanged is sent instead.

    In the payloads of the a11y messages every value is a JSON string, as
    the engine writes them, except inputSequence, which is a number, an
    empty array is written as "", and an offset counts UTF-16 code units
    of the accessible text of a paragraph. The payload is a paragraph
    object:

        {"content": "<text>", "position": "<offset>", "start": "<offset>",
         "end": "<offset>", ...}

    content is the accessible text of the paragraph, position the caret,
    start and end the selection as for a11ytextselectionchanged. These
    members follow only where they have a value:

    listPrefixLength: the length of the bullet or number at the start of
        content.
    headingLevel: the outline level of a heading, from 1.
    area: "header", "footer", "footnote" or "endnote", for a paragraph
        outside the body text.
    links: [{"start", "end", "url"}], the hyperlinks.
    formats: [{"start", "end", ...}], the runs of character formatting,
        with "bold", "italic", "underline" and "strikethrough" as "true"
        where set, and "escapement" as "super" or "sub".
    changes: [{"start", "end", "type", "author", "dateTime"}], the tracked
        changes shown; type is "insertion", "deletion" or "attributes";
        author and dateTime (ISO 8601 in whole seconds, always with the
        time of day and with no zone) are present where known.
    images: [{"position", "name", "description", "kind", "shapeType"}],
        the objects anchored as characters; position is the offset of the
        object character, kind is "shape", "frame", "formula", "chart" or
        "object" and absent for an image, and shapeType, such as
        "Rectangle", is there for a shape only.
    comments: [{"start", "end", "id", "author", "text"}], the range of
        each comment and its id as in the comment message.
    contentControls: [{"start", "end", "type", "alias", "checked",
        "placeholder"}]; type is "richText", "plainText", "checkbox",
        "dropDown", "comboBox", "picture" or "date", alias is there where
        set, checked is "true" or "false" for a checkbox, and placeholder is
        "true" while the placeholder text shows.
    before, after: the text of the paragraphs around this one in the same
        text, in document order: those within the visible area extended by
        its height above and below, or 10 on each side when the visible area
        is not known. The paragraphs given in list and table are left out.
        The two come together, with their rectangles: where only one side
        has paragraphs, the other is "".
    beforeRects, afterRects: their rectangles in twips, as "<x>, <y>,
        <width>, <height>": in document coordinates in Writer, and from the
        top left of the shape or cell being edited elsewhere.
    beforeLevels, afterLevels: their heading levels, 0 for a paragraph
        that is no heading, both present where a paragraph of either side
        is a heading.
    beforeLinks, afterLinks, beforeFormats, afterFormats, beforeChanges,
        afterChanges, beforeImages, afterImages, beforeComments,
        afterComments, beforeContentControls, afterContentControls: one
        array per paragraph of that side, as for this one, present where a
        paragraph of that side has such elements.
    list: {"items": [{"level", "text", "rect"}]}, for a Writer paragraph
        with a bullet or a number outside tables: the run of list
        paragraphs including this one, up to 25 on each side, with the list
        level from 0 and the rectangle as for beforeRects.
    table: {"rowCount", "colCount", "rows": [{"row", "cells": [{"col",
        "text", "rowSpan", "colSpan"}]}]}, for a Writer paragraph in a
        table: the rows of the innermost table holding it, from 25 above
        the caret's row to 25 below it. text holds the paragraphs of a cell
        joined by "\n", a nested table as its cells' text, one per line; a
        span is there only when above 1.
    force: "1" when the paragraph was changed by another view, or when
        editing the text of a selected shape or a spreadsheet cell starts,
        so the client updates its copy even while it is composing.

a11yfocusedparagraph: <payload>

    The answer to geta11yfocusedparagraph, a paragraph object as for
    a11yfocuschanged.

a11ycaretposition: <offset>

    The answer to geta11ycaretposition: the caret in the accessible text
    of the paragraph that has the accessibility focus, as a plain number.

a11yfocusedcellchanged: <payload>

    Sent while screen reader support is on, in place of a11yfocuschanged,
    when the caret goes to a paragraph in a Writer table, another paragraph
    of the same cell included, or out of all tables. JSON payload:

        {"outCount": "<count>", "inList": [{"rowCount", "colCount"}],
         "row": "<row>", "col": "<column>", "rowSpan": "<rows>",
         "colSpan": "<columns>", "paragraph": {...}}

    outCount is the number of tables the caret left, inList the size of
    each table it entered, the outermost first, both absent when there is
    none. row and col count from 0, and are -1 when the caret left all
    tables; a span is there only when above 1, and paragraph is the
    paragraph object of the caret, as for a11yfocuschanged.

a11yeditinginselectionstate: <payload>

    Sent while screen reader support is on, when editing the text of a
    selected shape starts or ends, or when editing a spreadsheet cell
    starts; the end of editing a cell is an a11yfocuschanged with empty
    content and position 0, whose other members still hold the cell's
    values. JSON payload:

        {"cell": "<0|1>", "enabled": "<0|1>", "selection": "<name>",
         "paragraph": "<text>"}

    cell is 1 for a spreadsheet cell, enabled is 1 when editing starts,
    selection is the address of the cell or the name of the shape, and
    paragraph the text of the paragraph that has the accessibility focus;
    selection and paragraph are there only when editing starts, and
    paragraph only when the text being edited has a single paragraph.

a11yselectionchanged: <payload>

    Sent while screen reader support is on, when an object or a table cell
    is selected, leaves the selection, or is deleted while selected. JSON
    payload:

        {"cell": "<0|1>", "action": "<action>", "name": "<name>",
         "text": "<text>", "contentControl": {...}}

    cell is 1 for a table cell. action is "create" when the selection is
    this object alone, "add" when a Writer shape joins the selection,
    "remove" when it leaves it and "delete" when the selected object is
    deleted. name is the name of the object, or of the table of a floating
    table. On "create" and "add", text holds the start of the text. For a
    cell it is at most 1000 characters. For an object it is its first 10
    paragraphs, or for a floating table the first 10 paragraphs of each of
    its first 10 cells; each one that is not empty is followed by " \n"
    unless cut short, and all of them hold at most 1000 characters,
    separators not counted, or 100 for a text frame, a floating table
    included. Text cut short ends before its last space, where it has one,
    and text is absent when empty.
    contentControl, as an element of contentControls in a11yfocuschanged
    without the range, is there for an object in a content control.

a11ycaretchanged: <payload>

    Sent while screen reader support is on, when the caret moves inside
    the paragraph that has the accessibility focus. JSON payload:

        {"position": "<offset>", "inputSequence": <sequence>}

    <offset> is the caret in the accessible text of the paragraph.
    inputSequence is the newest input of the view applied before the caret
    was placed, absent while the client numbers no inputs, so a client that
    moves the caret ahead of the server can find which of its Left and Right
    keys a report does not include yet.

a11ytextselectionchanged: <payload>

    Sent while screen reader support is on, when the text selection in
    the paragraph that has the accessibility focus changes. JSON payload:

        {"start": "<offset>", "end": "<offset>", "inputSequence": <sequence>}

    end is the end of the selection that holds the caret, start the other
    one, both in the accessible text of the paragraph, and both -1 when
    nothing is selected. inputSequence is as for a11ycaretchanged.

cellcursorstate: <payload>

extractdocumentstructure url=<documentURL> filter=<filterType>

    Extracts structured data from a document and returns it in JSON format.

    - url=<documentURL> : Specifies the document location.

    - filter=<filterType> : (Optional) Limits extraction to specific elements (e.g., text, contentcontrol, charts, docprops, slides). If omitted, all available data is extracted.

    remotedocsubscribe, named by the persistent link its remote link is
    bound to. The tag is the session id of the view that opened the
    subscription. The engine does not read these events yet, and the views
    learn the state of their links from the remotelinks message. <event> is
    one of:

    * 'modified': the remote document's modified state changed to <value>

      burst of changes

    * 'failed': the connection is given up until a new subscription

    * 'unsubscribed': the link was dropped on request

      'notfound' for a persistent link no remote link is bound to and
      'notoken' for a source the view holds no token for

Admin console
===============

Client can query admin console to get information about currently opened
documents. Following information about the document is exposed:

* PID of the process hosting the document
* Number of client views opening this document
* Name of the document (URL encoded)
* Memory consumed by the process (in kilobytes)
* Elapsed time since first view of document was opened (in seconds)

Admin console can also opt to get notified of various events on the server. For
example, getting notified when a new document is opened or closed. Notifications
are commands sent from server to the client over established websocket.

Before doing anything, clients must authenticate by providing an auth token with
'auth' command.

/co/collab WebSocket endpoint
=============================

The /co/collab WebSocket is separate from the per-document /cool/ws session.  A CODA or COWASM
client opens it to coordinate with any other clients editing the same document: it surfaces a
per-doc user list, lets peers signal that local editing has started, and exchanges document bytes
through one-shot HTTP byte-stream URLs.  One CollabBroker per docKey lives on the server side and
brokers all messages for that document.

Connection:

    wss://<host><service-root>/co/collab?WOPISrc=<wopi-url>

    The server refuses the upgrade with 400 when WOPISrc is missing, or when
    client_document_loading.enable in coolwsd.xml is off.  The first message from the client is

        access_token <token>

    with the URI-encoded access token for <wopi-url>.  The server sends "progress: validating",
    ignores further messages while it checks the WOPI host and calls CheckFileInfo, and derives
    the docKey of the document from <wopi-url>, the same as for the /cool/ws session of the
    document.  It replies with one of

        error: cmd=collab kind=accesstoken
        error: cmd=internal kind=unauthorized[ code=<base64 SSL verification message>]
        error: cmd=internal kind=timeout
        error: cmd=storage kind=loadfailed

    and closes the WebSocket on failure ("kind=accesstoken" when the first message is not
    "access_token <token>"), or sends {"type":"user_list",...} and then {"type":"authenticated",...}
    on success.  From then on, every message in either direction is a single JSON object with a
    "type" field.

server -> client messages on /co/collab
---------------------------------------

{"type":"authenticated","fileInfo":{...}}

    Sent once the wopiSrc + access_token pair has been accepted.  "fileInfo" holds the file
    properties of the wopi: message to a /cool/ws session, such as "UserCanWrite", "EnableShare"
    and the "Hide..." and "Disable..." options.  It leaves out "FileUrl", as the document comes
    through fetch, and the values that only a /cool/ws session has: "TemplateSource" and the AI
    settings.

{"type":"user_list","users":[<user>,...],"editingActive":<bool>}

    Initial snapshot of the connected user set, sent right before {"type":"authenticated"} (and
    left out when the server is shutting down).  It covers the users of the other /co/collab
    connections and of the /cool/ws sessions on the same document.  The broker only tracks the
    /cool/ws sessions while a /co/collab connection is open, so for the first connection they
    arrive after {"type":"authenticated"}, as {"type":"user_joined"} (followed by
    {"type":"editing_started"} for one that can write).  Each <user> object carries "id" (the
    integrator user id) and "name" (display name), and here also "canWrite" (true if this view
    holds write access).  When a user of a /co/collab connection has an avatar registered with the
    broker, the object also carries "avatar":"<path>" pointing at the /co/collab/avatar endpoint
    described below.  "editingActive" is true once any peer has sent {"type":"editing_started"}, or
    a /cool/ws session that can write has joined.

{"type":"user_joined","user":<user>}
{"type":"user_left","user":<user>}

    A peer connected or disconnected, also one of a /cool/ws session.  Sent to every other client.
    The <user> of "user_joined" also carries "canWrite", the one of "user_left" does not.

{"type":"editing_started","user":<user>}

    Some peer transitioned from viewing to editing.  Sent each time a client sends
    {"type":"editing_started"}, and when a /cool/ws session that can write joins.  The broker
    tracks an "editing started" flag, so a late-joining client gets the same information through
    user_list's "editingActive".  The <user> carries "canWrite" only for a /cool/ws session.

{"type":"switch_to_collab","user":{"id":"<id>","name":"<name>"}}
{"type":"saved_and_switching","user":{"id":"<id>","name":"<name>"}}

    Sent during a local-to-server transition.  "switch_to_collab" comes from a peer that wants to
    join collaborative editing, and only reaches a peer whose user sent {"type":"editing_started"}.
    "saved_and_switching" comes from a peer that edited a local copy, once it has saved that copy
    back to the integrator or has nothing to save.

{"type":"fetch_url","stream":"<name>","requestId":"<id>","url":"<url>",...}

    Reply to a client-sent {"type":"fetch"}: the one-shot URL that the client can GET to download
    the bytes of the stream, as a path (/co/collab/fetch?token=<one-shot-token>, without host and
    without service root).  For the "contents" stream, the reply also carries "filename":"<name>"
    with the document filename and "lastModifiedTime":"<time>" with the version in storage, when
    known, both as of the CheckFileInfo when the connection signed in.

{"type":"fetch_error","stream":"<name>","requestId":"<id>","error":"<text>"[,"cleanExport":false]}

    Reply to a client-sent {"type":"fetch"} that cannot be served ("Stream not available",
    "Session expired", "Server shutting down").  A fetch of the document bytes ("contents",
    "fileUrl" or "templateSource") by a user whose integrator disallows a clean copy (DisableExport,
    DisableCopy or WatermarkText) carries "error":"Export not allowed" and "cleanExport":false; such a
    user can open the document only through /cool/ws.

{"type":"upload_url","stream":"contents","requestId":"<id>","url":"<url>"}

    Reply to a client-sent {"type":"upload"}: the one-shot URL that the client can POST the
    modified document bytes to, as a path (/co/collab/put?token=<one-shot-token>, without host and
    without service root).

{"type":"upload_error","stream":"<name>","requestId":"<id>","error":"<text>"}

    Reply to a client-sent {"type":"upload"} that cannot be served ("Upload only supported for
    contents stream", "The host allows this user no writes", "Session expired", "Server shutting
    down").

{"type":"error","error":"<text>"[,"requestId":"<id>"]}

    The client sent a malformed frame ("Invalid JSON", "Invalid JSON object", or "Unknown message
    type", the latter with the "requestId" of the message).

client -> server messages on /co/collab
---------------------------------------

{"type":"fetch","stream":"<name>","requestId":"<id>"}

    Request a one-shot URL for downloading the bytes of a stream: "contents" (the default, the
    current document bytes), "fileUrl" (the document from the integrator's FileUrl),
    "templateSource" or "userSettings".  Server replies with {"type":"fetch_url"} (success) or
    {"type":"fetch_error"} (failure), carrying the same "requestId" so the client can correlate
    replies with requests (and none when the request had none).

{"type":"upload","stream":"contents","requestId":"<id>"[,"lastModifiedTime":"<time>"]}

    Request a one-shot URL for uploading modified document bytes.  Server replies with
    {"type":"upload_url"} (success) or {"type":"upload_error"} (failure), with "requestId" as for
    "fetch".  With "lastModifiedTime",
    the upload is refused with 409 if storage no longer has the version of that time.  The client
    gets that time as "lastModifiedTime" in the {"type":"fetch_url"} for the "contents" stream, and
    then as "LastModifiedTime" in the JSON that each successful /co/collab/put returns.

{"type":"editing_started"}

    This view has just transitioned from viewing to editing.  Broadcast as
    {"type":"editing_started","user":<self>} to every other client and sticks the "editingActive"
    flag in subsequent user_list snapshots.

{"type":"switch_to_collab"}
{"type":"saved_and_switching"}

    Drive the local-to-server transition: a peer that wants to join collaborative editing sends
    "switch_to_collab", and a peer that edits a local copy answers with "saved_and_switching" once
    it has saved that copy back to the integrator or has nothing to save.  The server does not tie
    the two together.  "switch_to_collab" is forwarded to the
    other peers whose users sent {"type":"editing_started"}, and "saved_and_switching" to all other
    peers, both with the sender's user object added.

{"type":"bye"}

    Sent right before the client closes the WebSocket as an orderly disconnect marker.  When the
    last connection of a document closes without it, the broker keeps its state (such as
    "editingActive") for an idle grace period of 30 seconds in case the client reconnects; "bye"
    lets the broker reclaim itself immediately.

HTTP byte-stream endpoints under /co/collab/
--------------------------------------------

These endpoints are reached over the same origin that serves the WebSocket.  /co/collab/fetch and
/co/collab/put allow cross-origin reads (Access-Control-Allow-Origin: *, and /co/collab/put also
answers the OPTIONS preflight), so a CODA page on a different origin can drive them.  Their
one-shot token is what authenticates a request.

/co/collab/fetch?token=<one-shot-token>

    GET.  Returns the bytes of the stream that the matching {"type":"fetch"} WS request resolved
    to.  The token is one-shot: it is consumed by the first request, also one that then fails, and
    it expires after 5 minutes.  The reply is 400 without a token, 401 for an unknown or expired
    token, 410 when no /co/collab connection to the document is open (also during the grace period
    described for {"type":"bye"}), and 403 or 502 when the integrator refused or failed.

/co/collab/put?token=<one-shot-token>

    POST.  Accepts modified document body bytes from a peer that requested an upload URL via
    {"type":"upload"}.  Same one-shot token semantics and replies, plus 409 as described for
    {"type":"upload"}.  On success, the reply is 200 with the integrator's PutFile answer.

/co/collab/avatar?WOPISrc=<wopi-url>&userId=<user-id>&token=<access-token>

    GET.  Returns the avatar bytes for the user, fetched by the server from the URL the integrator
    supplied in WOPI's UserExtraInfo.avatar so the client never sees integrator-internal URLs.
    <access-token> is the access token of the document's /co/collab connections, which changes
    every 5 minutes (the previous one stays valid until the next change), and the client gets the
    whole URL as "avatar" in a <user> object.  No message renews that URL, so it stops working
    after the second change.  The reply is 400 when a parameter is missing, 410 when no /co/collab
    connection to the document is open, 401 for an access token that is no longer valid, and 404
    when the user has no avatar.
