# Software Bill of Materials

Collabora Online ships SBOMs describing everything in the product: the
server, the browser client, the Collabora Office engine underneath, and — for
the container images — the base image and the distribution packages on top of
it. This document explains how those documents are generated, how to check
them, and how to scan them for known vulnerabilities.

If you are here because a scan came back clean and you want to know whether
to believe it, read [What a scan does not tell you](#what-a-scan-does-not-tell-you)
first. The short version: a clean scan is not evidence that a component has
no known vulnerabilities.

## What is generated, and where

Three documents at three levels of granularity, each generated by the build
that produces the thing it describes.

| Level | Format | Generator | Output |
| --- | --- | --- | --- |
| Engine, one document per distro package | SPDX 3.0.1 | `engine/solenv/bin/create-sbom.py` | `engine/workdir/CustomTarget/instsetoo_native/sbom/<package>-sbom.spdx.json`, copied to `engine/instdir/sbom/` |
| Online (coolwsd + browser) | SPDX 3.0.1 | `scripts/create-sbom.py` | `collabora-online-sbom.spdx.json` |
| Container image | CycloneDX 1.6 **and** SPDX 3.0.1 | `docker/from-packages/scripts/generate-image-sbom.py` | `/usr/share/sbom/collabora-online.cdx.json` and `collabora-online-image-sbom.spdx.json` inside the image |

The two SPDX documents follow the same conventions — per-file SHA512 hashes
with BSI TR-03183-2 purpose flags, externals identified by CPE with their
source tarball and its SHA256, static linking expressed as `contains` with
`software_softwareLinkage: "static"` — so they can be read as one set.

### Engine

Generated as part of packaging, gated on `PKGFORMAT` being set or
`LIBO_TEST_INSTALL=TRUE`, and only from a top-level `make` (a partial build
has no static-link data and the recipe refuses to run). To produce them in a
development tree:

    cd engine && make LIBO_TEST_INSTALL=TRUE CustomTarget_instsetoo_native/sbom

`solenv/bin/modules/installer.pm` then puts each document into its own
package, so every `.deb`/`.rpm` carries `<package>-sbom.spdx.json` at its
install root (`/opt/collaboraoffice<version>/`).

Component metadata that cannot be discovered mechanically — vendor, homepage,
declared and concluded license — comes from the HTML comments in
`engine/readlicense_oo/license/license.xml`:

    <!-- Name: curl, Vendor: haxx, Source: CURL_TARBALL, URL: https://curl.se/,
         Declared: curl, Concluded: MPL-2.0 -->

`Source` is either a `*_TARBALL` variable from `engine/download.lst` (version
and SHA256 are then taken from there, and the download URL from the matching
bucket in `engine/Makefile.fetch`) or a path in the source tree. Everything
else — which files belong to which package, what links what, which libraries
come from the operating system — is derived from scp2, the packinfo files, the
gbuild externals annotations and the built binaries themselves.

### Online

Generated by the normal build and installed as part of the coolwsd package:

    make collabora-online-sbom.spdx.json      # or just: make

It lands in `/usr/share/coolwsd/` (not the doc directory, so that it survives
the container image's `/usr/share/doc` trim and is included in the `.deb`).
Versions come from the engine build tree rather than from compiled-in macros,
so no binary has to be executed and cross builds work.

Its inputs: `engine/download.lst` for the statically linked C++ externals,
the unpacked POCO tarball for the sources bundled inside POCO,
`browser/npm-shrinkwrap.json` for the runtime npm dependency closure,
`gbuild/Executable_*.mk` for what links what (cross-checked against each
binary's `DT_NEEDED`), and `scripts/sbom-externals.json` for vendored code and
metadata.

### Container image

`docker/from-packages` generates the image-level SBOMs in a dedicated `sbom`
build stage, merging:

* the **base image's** own CycloneDX SBOM. ZenDiS publishes it as a cosign
  attestation, which `docker/from-packages/scripts/fetch-base-sbom.py` pulls
  from the registry;
  `--build-arg sbom_base=` selects `fetch` (default), `file` (supply
  `base-sbom*.cdx.json` in the build context, for air-gapped builds), `probe`
  (read the base image's own dpkg metadata, for a Debian or distroless base)
  or `none`. `--build-arg sbom_strict=1` fails the build instead of degrading.
* one **`pkg:deb` component per shipped package**. Debian-repository packages
  get `pkg:deb/debian/...`, which scanners match against the Debian security
  tracker; Collabora-published ones get `pkg:deb/collabora/...` and are
  deliberately not distro-matchable, because no distro feed covers them.
* the **per-package SPDX documents inside the image**, referenced by path and
  SHA256, *and* their component inventory lifted into the CycloneDX component
  list — because most scanners cannot read SPDX 3.x, and without the lift a
  scan of the image SBOM would only see the Debian layer and nothing of
  Collabora Online's own contents.

A `collabora:sbom-completeness` property records which of those inputs were
actually present.

## How to check the SBOMs

Three checks, in increasing order of external dependencies.

### `make sbom-check` — internal consistency

No dependencies, safe in CI, and the one to run after touching dependencies.
It verifies that the annotations in `scripts/sbom-externals.json` agree with
reality: every external some binary links has an entry and vice versa, the
sources bundled in POCO match what POCO actually contains, the shipped npm
list agrees with the shrinkwrap, the static-link table agrees with
`gbuild/Executable_*.mk`, no installed file is listed twice — and that every
direct dependency appears in `THIRDPARTYLICENSES`, which is the project
policy (direct dependencies are listed there, transitive ones only in the
SBOM).

The engine has the equivalent built into its generator: it fails the build on
an unused `license.xml` annotation, a duplicate installed file, or a package
root with no files.

### `make sbom-audit` — are the identifiers matchable?

    grype db update      # once, to have a database
    make sbom-audit

Cross-checks every `cpe23` identifier our SBOMs assert against grype's
vulnerability database and reports the ones that *under-match* — where another
vendor of the same product carries more CVEs than the vendor we assert.
Requires the grype database locally (found via `GRYPE_DB_CACHE_DIR` or
`~/.cache/grype/db`); no network.

This exists because an unmatchable identifier is invisible: the scan comes
back clean and looks exactly like a component with no known vulnerabilities.
`--show-unknown` additionally lists components whose product name appears in
no CPE at all, which is mostly small libraries the CPE dictionary does not
cover, hence off by default.

### `make sbom-freshness` — is anything behind upstream?

    make sbom-freshness

Asks [release-monitoring.org](https://release-monitoring.org) what upstream
currently ships and reports what we bundle that is older. Needs network
access and takes a couple of minutes for a full sweep; `--component NAME`
(repeatable, script only) narrows it to specific components. Exit code 1 if
anything is behind, so it can gate a scheduled CI job — which is where it
belongs, because this check, not scanning, is the primary defense for C
components (see below).

Note that the engine document it reads must already have been generated; it
is not a make prerequisite.

## How to scan for vulnerabilities

**Scan the SBOM, not the image filesystem.** The container ships no dpkg
database, and the Collabora-published packages match no distro security feed
in any case. What makes the product's contents visible to a scanner is the
component inventory in the SBOM: the engine's externals carry CPEs, the npm
dependencies carry purls.

    # extract the image-level SBOM
    id=$(docker create <image>) && docker cp $id:/usr/share/sbom/collabora-online.cdx.json . && docker rm $id

    trivy sbom collabora-online.cdx.json      # matches pkg:deb and npm purls
    grype sbom:collabora-online.cdx.json      # additionally matches CPEs

The two are complementary and you want both: trivy resolves the Debian
packages and the npm advisories, while grype also does CPE matching, which is
what surfaces the statically linked C libraries. The CycloneDX document
carries an `operating-system` component (`debian 13`) so that scanners key the
`pkg:deb` components to the right feed.

Expect false positives from CPE matching, for two reasons: NVD version ranges
are frequently wrong, and the engine backports security fixes into bundled
tarballs without bumping their version, which version-based matching cannot
see. That is what the VEX is for.

## VEX: triaging what the scan reports

`docker/from-packages/vex/cool.vex.json` is a CycloneDX VEX document
recording, per CVE, whether the product is actually affected — Collabora is
the supplier of these packages, so nobody else can make these statements.

`docker/from-packages/scripts/publish.sh` scans the SBOM at publish time and
appends new findings as `in_triage` (via `generate-vex.py`); a human then sets
the state. Useful states, with the evidence each needs:

| State | Means | Evidence to record |
| --- | --- | --- |
| `not_affected` | the vulnerable code is not in our build | the configure flag or build file that excludes it |
| `resolved_with_pedigree` | fixed by a backported patch | the patch file in `engine/external/<component>/` |
| `false_positive` | the advisory does not apply to this component or version | why: fixed before the version we ship, or a product name collision |
| `in_triage` | not yet assessed | what has to be established to close it |

Keep `in_triage` entries honest rather than tidy: an unassessed CVE that is
marked `not_affected` is worse than one that admits it needs work.

## Publishing

`docker/from-packages/scripts/publish.sh` publishes an image the way ZenDiS
publishes the hardened base images: a cosign signature plus attestations —
CycloneDX SBOM, SPDX SBOM, a trivy scan in SARIF, the VEX document, and SLSA
provenance — attached as `sha256-<digest>.sig`/`.att` sidecar tags on every
per-platform manifest digest. It is registry-agnostic; see section 8 of
`docker/README` for the invocation and for how consumers verify with
`cosign verify-attestation`.

## What a scan does not tell you

Three ways a vulnerability scan of a correct, complete SBOM stays silent about
a real problem. All three have bitten this project.

1. **An unmatchable identifier.** The SBOM said
   `cpe:2.3:a:curl_project:curl:8.14.1` — a real entry in the CPE dictionary,
   but one carrying a single unrelated CVE about an abandoned Ruby gem of the
   same name. NVD keys curl's CVEs to the vendor `haxx`. With the vendor
   corrected, the same SBOM and the same scanner reported **33 CVEs, six of
   them Critical**. Counterintuitively, a *wrong* vendor is worse than none at
   all: an empty `Vendor:` becomes a `*` wildcard that matches every vendor of
   the product, while a misspelled one matches only itself. A wrong *product*
   name is worse still, since the wildcard cannot compensate — NVD calls expat
   `libexpat` and zstd `zstandard`. `make sbom-audit` exists to catch this.

2. **No answer to "is there a newer release?"** A scanner reports the CVEs a
   version is known to be affected by; it never says that upstream has moved
   on. Being behind is not a vulnerability, but it is how one becomes one, and
   it is the lead time for a bump that turns out to need work.
   `make sbom-freshness` exists to catch this.

3. **Recently published CVEs are unmatchable for CPE-only components.** Expat
   2.8.2 was affected by five CVEs (four fixed in 2.8.4, upstream CVSS up to
   7.5). All four were present in a two-day-old grype database — with *no CPE
   applicability data*, because NVD had not enriched them yet. Expat is a C
   library with no purl, so CPE matching is the only mechanism that could
   match it, and there was nothing to match against. Nothing about the scan
   looked wrong.

The practical consequence: for the bundled C libraries, **keeping components
current and reading upstream release notes is the primary control, and
scanning is the backstop** — not the other way round. Never conclude "this
component has no known vulnerabilities" from a clean scan; check the upstream
changelog (the `Changes` or `NEWS` file in the tarball is authoritative) and
the project's security advisories.

## Maintenance tasks

**Adding a third-party dependency.** Add it to `THIRDPARTYLICENSES` if it is
a direct dependency (policy: direct there, transitive only in the SBOM), and
annotate it: `engine/readlicense_oo/license/license.xml` for engine externals,
`scripts/sbom-externals.json` for online's. Then run `make sbom-check`, which
fails if the two disagree. When filling in the `Vendor` field, check it
against the CPE dictionary — or leave it empty, which is safe.

**Bumping a bundled component.** Edit `engine/download.lst` (tarball and
SHA256); everything downstream — the SBOM version, the source URL, the CPE —
follows automatically. If the component is not on the LibreOffice mirror, add
or update its bucket in `engine/Makefile.fetch`; the SBOM takes the source
URL from there. Record the CVEs the bump fixes in the commit message, from
upstream's changelog.

**Checking the whole chain.** `make sbom-check`, `make sbom-audit`,
`make sbom-freshness`, then regenerate and scan as above.
